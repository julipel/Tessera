# ADR-0023: Повтор хода — новый ответ на сохранённый ввод, неудачный помечается заменённым

- Статус: принято
- Дата: 2026-10-05

## Контекст
В P5-07 «Повторить» отправляет тот же ввод ещё раз с новым `client_message_id`. В БД
остаются оба сообщения пользователя и неудачный ответ. История для модели
(`to_llm_messages`) пропускает ответы без текста, поэтому модель получает один вопрос дважды
подряд. Если сбой случился после первых кусков текста, модель видит ещё и обрывок ответа.
После перезагрузки страницы «Повторить» пропадает: ошибка хода в истории не сохраняется.

## Решение
1. **`POST /v1/conversations/{id}/messages/{message_id}/retry`**, ответ — SSE-стрим, как
   у `POST …/messages`. `message_id` — id **неудачного ответа ассистента**, а не сообщения
   пользователя: id ответа клиент знает из событий хода и истории, а id своего сообщения
   получает только из истории. Сервер сам берёт ввод из последнего сообщения пользователя
   перед этим ответом, нового сообщения пользователя не создаётся.
2. **Повторить можно только последний ответ диалога** со `status=failed` и
   `error.retryable=true`. Иначе (ответ успешный, ошибка неповторяемая, после ответа
   уже есть сообщения, указан id сообщения пользователя) — 409 `not_retryable`, новый
   HTTP-код. Ответа нет среди видимых сообщений (чужой, неизвестный, уже заменённый) —
   404 `not_found`. Ветвлений диалога нет.
3. **Неудачный ответ помечается заменённым**: `messages.replaced_by` = id нового ответа.
   Пометка ставится условным `UPDATE … WHERE replaced_by IS NULL` и фиксируется до начала
   стрима, поэтому из двух одновременных повторов ход запустит только один, второй
   получит 409. FK на `messages.id` нет: новый ответ записывается в конце хода.
4. **Заменённые сообщения не видны**: `MessageStore.list_for` их не возвращает, то есть их нет
   ни в `GET …/messages`, ни в контексте модели. В БД они остаются для разбора и логов.
5. **Ошибка хода сохраняется с ответом**: `messages.error` = `{code, message, retryable}`,
   то есть данные SSE-события `error`. В `HistoryMessage` она отдаётся как необязательное
   поле `error`, и клиент показывает «Повторить» и после перезагрузки.
6. Побочные эффекты неудачной попытки не откатываются. Завершённые вызовы инструментов
   записаны к заменённому ответу, изменённый DialogState сохранён. Повторный ход
   начинается с текущего состояния.

## Альтернативы
- **Повтор через `POST …/messages` с тем же `client_message_id`.** Этот запрос по контракту
  означает «ход уже был» (409 `duplicate_message`). Если сделать его повтором, ретрай сети
  стал бы запускать второй ход.
- **`message_id` сообщения пользователя в пути** (так в первой формулировке roadmap). Клиенту
  пришлось бы получать id своего сообщения: добавлять его в SSE или перечитывать историю.
  Неудачный ответ однозначно определяет и ввод, и то, что заменяется.
- **Удалять неудачный ответ.** Пропадают данные для разбора сбоев и вызовы инструментов,
  уже выполненные в этой попытке.
- **Фильтровать неудачные ответы при сборке контекста модели.** Дубль вопроса остаётся,
  а в истории клиента остаются обе попытки.

## Последствия
- В контексте модели и в ленте один вопрос и один ответ на него.
- Клиент повторяет по id ответа. Если ответа нет (сбой до `turn_started`), клиент, как
  раньше, отправляет ввод заново (P5-08b).
- Защита от параллельных ходов в диалоге по-прежнему только в процессе (P7-06). Здесь
  гонку двух повторов закрывает условный UPDATE.
- Повторить прерванный ответ (`interrupted`) или «перегенерировать» успешный нельзя.
  Если понадобится, это будет отдельное решение.
