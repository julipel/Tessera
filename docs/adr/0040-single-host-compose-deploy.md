# ADR-0040: Деплой на один сервер — docker compose, Caddy и один домен

- Статус: принято
- Дата: 2026-10-14

## Контекст
Для пилота (P9-02) нужен постоянный публичный адрес: витрины `/demo/shop/*.html?key=…`,
виджет на сайтах тенантов, админка. Quick tunnel из P9-00b для этого не годится: адрес
временный и зависит от сети разработчика. Нагрузка пилота небольшая. По P7-05 один процесс
API выдерживает десятки одновременных ходов, а отмена хода уже работает между процессами
(ADR-0035). Кластер на этом этапе не нужен.

Ограничения:
- `NEXT_PUBLIC_API_URL` вшивается в сборку web;
- API находит `config/tenants` и `data/` от корня репозитория;
- файлы источников из админки пишет API, а читает worker (ADR-0037);
- SSE нельзя буферизовать на прокси.

## Решение
1. **Один сервер, docker compose** (`deploy/compose.prod.yml`): postgres, redis (с AOF),
   qdrant, migrate, api, worker, web, caddy. Образы собираются на сервере из рабочей копии
   репозитория (`make deploy-up`), registry не используется.
2. **Образы.** `apps/api/Dockerfile` — один образ для ролей api, worker и migrate (команду
   задаёт compose). Раскладка `/srv/apps/api` повторяет репозиторий. В образ вшиты
   `config/` и `data/pilot/`, поэтому `seed` работает внутри контейнера. `apps/web/Dockerfile` —
   Next.js `output: "standalone"`, а `NEXT_PUBLIC_API_URL` передаётся как build-arg.
3. **Один домен.** Caddy с автоматическим TLS: `/v1/*` и `/health` уходят в api, всё
   остальное — в web. Веб-чат, витрины и API живут на одном origin:
   `CORS_ORIGINS=["https://<домен>"]`, `NEXT_PUBLIC_API_URL=https://<домен>`. Для API-маршрутов
   сжатие выключено, поэтому SSE не буферизуется. Наружу открыты только 80 и 443.
4. **Миграции при деплое** — одноразовый сервис `migrate` (`alembic upgrade head`). Api и
   worker стартуют только после его успешного завершения (`service_completed_successfully`).
5. **Секреты** — `deploy/.env` на сервере, его нет в git, шаблон — `deploy/.env.example`.
   Адреса внутренних сервисов и `CORS_ORIGINS` выводятся в compose из `DOMAIN` и `POSTGRES_*`.
6. **IP посетителя** для лимитов (ADR-0030): uvicorn запущен с `--proxy-headers
   --forwarded-allow-ips *`. Порт API не опубликован, к нему ходит только Caddy из сети compose.
7. **CSP виджета.** Proxy страницы `/widget` обращается к API по `API_INTERNAL_URL`
   (`http://api:8000`), а не через публичный домен.
8. **Файлы источников** лежат в именованном томе `knowledge-files`, общем для api и worker.

## Альтернативы
- **Два поддомена (`app.` и `api.`).** Нужны две DNS-записи и два сертификата, CORS между
  origin, а витрины и чат всё равно живут на одном origin. Выигрыша нет.
- **PaaS (Render, Fly, Timeweb Apps).** Нужны отдельные сервисы для worker и общий диск для
  файлов источников. Привязка к платформе ради одного сервера не окупается.
- **Kubernetes или Swarm.** Избыточно для пилота. Compose-файл переносится, когда понадобятся
  реплики.
- **Registry и CI-сборка.** Правильно в перспективе, но пока деплоит один человек: сборка на
  сервере проще и не требует хранить учётные данные registry.
- **nginx.** Требует отдельного выпуска и продления сертификатов (certbot). Caddy делает это сам.

## Последствия
- Новый тенант выкатывается через `git pull && make deploy-up && make deploy-seed`: конфиги
  тенантов вшиты в образ API. Без пересборки тенанта можно править только через админку.
- Смена домена требует пересборки web (`NEXT_PUBLIC_API_URL`).
- Одна точка отказа — сервер. Бэкап Postgres делается вручную (`make deploy-backup`), без
  расписания. Qdrant восстанавливается переиндексацией (`make deploy-sync`).
- Для нескольких реплик API нужен балансировщик в Caddy. Отмена хода между процессами уже
  работает (ADR-0035), а файлы источников при этом пришлось бы перенести в объектное хранилище.

## Дополнение (P9-01am, 2026-10-17): изоляция хранилищ внутри сервера
Ревью безопасности выкладки (REVIEW.md: D-1…D-3) показало, что граница «наружу только 80/443»
не защищает хранилища от соседних контейнеров. Все сервисы сидели в одной сети, Redis и
Qdrant были без авторизации, а приложение ходило в Postgres суперпользователем. Достаточно
RCE в web (Node, открыт в интернет), чтобы положить в очередь arq задачу с pickle и выполнить
код в воркере со всеми секретами, прочитать или удалить векторы всех тенантов. Через
SQL-инъекцию в api при этом можно было получить shell в контейнере Postgres (`COPY … TO PROGRAM`).

Решение:
1. **Две сети.** `edge` (caddy, web, api) получает подсеть `COMPOSE_SUBNET`.
   `backend` (api, worker, migrate, postgres, redis, qdrant) не помечена `internal`,
   потому что api и worker ходят к LLM и сайтам источников. Web и Caddy хранилищ не видят.
2. **Redis с паролем** (`REDIS_PASSWORD`, `--requirepass`), **Qdrant с API-ключом**
   (`QDRANT_API_KEY`). Healthcheck Qdrant (`/readyz`) работает без ключа.
3. **Роль приложения** `APP_DB_USER` получает только DML на схему `public` и default
   privileges от владельца. Миграции идут владельцем `POSTGRES_USER`. Роль создаёт идемпотентный
   `deploy/postgres/app-role.sh` при первом запуске тома, для уже созданного тома — `make deploy-db-roles`.
   Пароль владельца нужен только compose для `DATABASE_URL` migrate. В окружении контейнеров
   его нет (`POSTGRES_PASSWORD: ""` поверх `env_file`), иначе RCE в api обходил бы роль.
4. Телеметрия Qdrant выключена.

Уточнение п. 6: после REVIEW.md S-5 uvicorn доверяет `X-Forwarded-For` не «*», а только
подсети `edge` (`FORWARDED_ALLOW_IPS=${COMPOSE_SUBNET}`). Иначе крайний левый адрес заголовка
подделывается, если перед Caddy окажется ещё один прокси.

Не делаем: JSON-сериализатор arq вместо pickle. После п. 1–2 писать в очередь могут только
api и worker, а у них и так есть все секреты. Аргументы задач (UUID и т. п.) пришлось бы
переводить в строки. Вернуться к этому стоит, если Redis станет общим с другими сервисами.

Последствия: в `deploy/.env` три новых обязательных секрета. Compose без них не стартует (`:?`),
API и воркер в production — тоже (`Settings`: пароль в `REDIS_URL`, `QDRANT_API_KEY`). Адреса
хранилищ (п. 5) выводятся теперь и из `APP_DB_*`, `REDIS_PASSWORD`, `QDRANT_API_KEY`.
Роль приложения может писать в `alembic_version` (default privileges на все таблицы):
подмена версии схемы требует SQL-инъекции и ломает только следующий migrate — принято.
Сбой healthcheck Redis теперь может означать и неверный пароль.
