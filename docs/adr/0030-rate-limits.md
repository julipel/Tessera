# ADR-0030: Лимиты частоты — фиксированное окно в Redis по IP и тенанту, при сбое Redis — пропуск

- Статус: принято
- Дата: 2026-10-07

## Контекст
P7-04a: лимиты по widget key / visitor и размер ввода. Виджет публичный, ключ виджета виден
в коде страницы: без лимитов любой может гонять ходы (вызовы LLM) за счёт тенанта.

- `visitor_id` придумывает клиент — лимит «по посетителю» обходится сменой id.
- API работает в нескольких процессах; Redis уже есть в инфраструктуре (arq), но процесс API
  к нему не подключён.
- Ошибка `rate_limited` (429, retryable) уже есть в контрактах; фронт на повторяемые HTTP-ошибки
  показывает «Повторить».

## Решение
1. **Порт `RateLimiter`** (`shared.kernel`): `hit(rule, subject) → RateDecision(allowed,
   retry_after_s)`. Реализации — `RedisRateLimiter` и `InMemoryRateLimiter` (тесты, свой на тест).
2. **Фиксированное окно:** ключ `rl:<правило>:<субъект>:<номер окна>`, `INCR` + `EXPIRE` одной
   транзакцией; `Retry-After` — секунды до конца окна.
3. **Правила** (настройки платформы, 0 — выключено): создание диалогов — 30 в час с IP; ходы
   (`messages` и `retry`) — 20 в минуту с IP и 300 в минуту на тенанта. Проверка — после ключа
   виджета (неизвестный ключ — 401, в лимиты не входит). Превышение любого правила — 429
   `rate_limited` с наибольшим `Retry-After`.
4. **Субъект «посетитель» — IP** (`request.client.host`); за обратным прокси uvicorn
   запускается с `--proxy-headers --forwarded-allow-ips` (P9-01).
5. **Redis недоступен — запрос пропускается** с warning в лог: лимит — защита от злоупотреблений,
   а не условие работы чата. Клиент Redis с таймаутами 0,5 с.
6. **Размер ввода:** `text` — `maxLength` 4000 в `user_input.schema.json` (и в поле ввода
   фронта); тело хода — до 32 КБ (`payload` кнопки, значения формы), иначе 422 `invalid_input`
   до записи ввода.

## Альтернативы
- **Скользящее окно / token bucket** (sorted set или Lua) — ровнее на границе окон, но сложнее;
  для защиты от злоупотреблений фиксированного окна хватает (на границе — до 2× лимита).
- **Лимит по `visitor_id` или диалогу** — обходится клиентом; IP тоже обходится (NAT, прокси),
  но дороже для атакующего; лимит тенанта ограничивает расход в любом случае.
- **Лимиты в памяти процесса** — не работают при нескольких процессах API.
- **Fail closed (без Redis — 429)** — падение Redis остановило бы все чаты.
- **Лимиты тенанта в AgentConfig** — нужны для разных тарифов; пока общие настройки платформы.

## Последствия
- Новая явная зависимость `redis` (уже стояла транзитивно через arq).
- Посетители за одним IP (офис, NAT) делят лимит ходов с IP.
- Тесты не используют Redis-счётчики, кроме теста самой Redis-реализации.
