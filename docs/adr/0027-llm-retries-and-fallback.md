# ADR-0027: Ретраи шага модели и резервная модель — до первого отданного чанка, резерв до конца хода

- Статус: принято
- Дата: 2026-10-07

## Контекст
P7-01, architecture.md §12: таймаут, 5xx или 429 LLM — ретрай с backoff, затем резервная модель,
затем `error` с `retryable: true`. Пустой ответ — один повтор, затем fallback-фраза.

Что уже есть:
- SDK OpenAI и Anthropic повторяют HTTP-запрос до начала стрима (`max_retries=2`,
  экспоненциальный backoff, `Retry-After`). Ошибка посреди стрима (`response.failed`, обрыв)
  и ошибка после ретраев SDK доходят до хода как `LLMError(retryable=True)`, и ход падает.
- `model.fallback` в AgentConfig есть, но не используется.
- Ответ стримится клиенту по мере генерации: после первого `text_delta` повтор шага
  задублировал бы текст в чате.
- `provider_items` (ADR-0010) — зашифрованный reasoning конкретной модели; другая модель
  его не примет.

## Решение
1. **`FallbackLLM`** (`agent/application/fallback_llm.py`) — `LLMClient` хода поверх клиента
   основной модели. Собирает его `LoopTurnAgent` по `model.primary` и `model.fallback`, поэтому
   поведение одинаково в chat API и эвалах.
2. **Повтор — только до первого чанка шага.** Повторяется `LLMError` с `retryable`, пока клиенту
   ничего не отдано (ни текста, ни `tool_started`). Ошибку после первого чанка обёртка
   пробрасывает: ход падает с `llm_unavailable`, дальше «Повторить» (ADR-0023).
3. **Порядок:** основная модель — 2 попытки с паузой 1 с, затем резервная — 1 попытка; HTTP-ретраи
   SDK — внутри каждой попытки. Константы ядра (`PRIMARY_ATTEMPTS`, `RETRY_DELAY_S`), не конфиг
   тенанта. Неповторяемая ошибка (400, нет ключа) пробрасывается сразу.
4. **Резервная модель — до конца хода.** После перехода следующие шаги хода идут сразу в неё.
   Из запроса к ней убираются `provider_items`. Клиент резервной создаётся при первом переходе;
   если провайдер не настроен — в лог `llm.fallback_unavailable`, наружу исходная ошибка основной.
5. **Пустой ответ** — нет вызовов инструментов и клиент за ход ещё ничего не увидел (ни текста,
   ни компонента): один повтор шага, затем fallback-фраза и `FinishReason.EMPTY_RESPONSE`
   (внутренний, в SSE не уходит). Пустой последний шаг после текста или компонентов — обычный
   конец хода.
6. Логи: `llm.retry`, `llm.fallback`, `agent.empty_response` (tenant/conversation/trace — из
   contextvars).

## Альтернативы
- **Буферизация шага и повтор после частичного ответа.** Клиент перестал бы видеть стрим до конца
  шага (латентность до первого токена — ключевая метрика), либо нужен откат уже показанных
  блоков в протоколе SSE. Ошибка посреди стрима редка, для неё есть «Повторить».
- **Ретраи только в SDK (`max_retries`) без своих.** Не покрывают ошибки внутри стрима
  (`response.failed` Responses API) и не дают перехода на резервную модель.
- **Свои ретраи вместо SDK (`max_retries=0`).** Потеряли бы `Retry-After` и разбор кодов
  ошибок SDK; одинаковое поведение для трёх провайдеров пришлось бы писать заново.
- **Резерв на один шаг, затем снова основная.** Лишняя попытка на недоступную модель на каждом
  шаге; смешение моделей внутри хода без пользы.
- **Число попыток в AgentConfig.** Пока нет потребности тенантов — меняется контракт ради
  констант.

## Последствия
- Недоступная основная модель с настроенным резервом не роняет ход, а ответ приходит от
  резервной; без резерва ход падает, как раньше, но после повтора (до ~1 с задержки + ретраи SDK).
- e2e-мок модели (`apps/web/e2e/mock-llm.mjs`) проваливает «сбой» `PRIMARY_ATTEMPTS` раз —
  при изменении числа попыток менять оба места.
- Суммаризатор (`summary_model`) резерва не получает: его ошибка на ход не влияет (ADR-0024).
