# ADR-0024: Сводка истории — asyncio-задача в процессе API после хода

- Статус: принято
- Дата: 2026-10-06

## Контекст
P6-02a добавила use case `summarize_conversation`: он сворачивает старую часть истории
в накопительную сводку и записывает её условно, по прежней границе. Нужно решить, кто и когда
его запускает. Сводка — один вызов модели на несколько секунд. Если сводки нет, ход всё равно
работает, просто с длинным контекстом. Пропущенная сводка ничего не ломает: история в БД
остаётся целиком. В проекте есть arq-воркер, но на нём только ingestion
(`sync_source`), а LLM-клиенты и AgentConfig диалогов собирает процесс API.

## Решение
1. **Когда.** После записи ответа хода (`TurnStream.save`, любой статус) проверяется порог
   по тем сообщениям, которые видела модель хода: история после сводки плюс новый ответ
   (`needs_summary`, политика `memory.fold_point`). БД при этом не перечитывается.
2. **Где.** asyncio-задача в процессе API (`chat.SummaryScheduler`). У задачи своя сессия
   БД из `session_factory`, потому что сессия стрима принадлежит ходу. Контекст structlog
   (tenant_id, conversation_id, trace_id) задача получает копией contextvars.
3. **Одна на диалог.** Пока по диалогу идёт сводка, новая не ставится. Между процессами
   гонку закрывает условная запись `update_summary`: записывается одна сводка, вторая
   отбрасывается (`summary_outdated`).
4. **Ошибки и потери.** Ошибка модели сводки или БД только логируется (`summary_failed`)
   и на ход не влияет. При остановке процесса незавершённые задачи отменяются (lifespan).
   Потерянную задачу восстанавливать не нужно: следующий ход снова увидит длинную историю
   и поставит сводку.

## Альтернативы
- **arq-задача (`job_id=summary:<conversation_id>`).** Даёт долговечность и дедупликацию
  между процессами. Но долговечность здесь не нужна: потерю чинит следующий ход. Зато
  появились бы сетевой переход через Redis на пути каждого длинного хода, задержка очереди
  (сводка может не успеть к следующему ходу) и сборка LLM-клиентов и конфигов в воркере.
- **Синхронно до `done`.** Клиент ждал бы ещё один вызов модели, а ошибка сводки стала бы
  частью хода.
- **В начале следующего хода.** Задержка попадает прямо в ответ пользователю.

## Последствия
- Пока сводка не записана, следующий ход идёт с полной историей после прошлой сводки.
  Это корректно, просто дороже.
- При нескольких воркерах API возможен лишний вызов модели сводки, но не две записи.
- Если сводка понадобится вне хода (пакетная переобработка, смена `summary_model`),
  для этого есть тот же use case. Перенос на arq — замена `SummaryRun`, без изменений хода.
