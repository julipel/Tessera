# ADR-0021: Подтверждение побочных эффектов — ожидающий вызов в состоянии, исполнение без модели

- Статус: предложено
- Дата: 2026-10-05

## Контекст
P5-04: `ToolDefinition.requires_confirmation` и компонент `confirm` были в контрактах, но
не работали. Первый такой инструмент — `create_lead` (заявка на консультацию). Побочный
эффект (заявка, бронь) нельзя доверять модели: она может создать его без согласия
пользователя, повторить или исказить аргументы после «да». По ADR-0004 UI — от бэкенда,
по ADR-0020 язык кнопок — в конфиге тенанта, не в ядре.

## Решение
1. Tool Registry не исполняет вызов инструмента с `requires_confirmation`: после проверки
   аргументов (JSON Schema и `ToolDefinition.check`) возвращает компонент `confirm`
   (`confirm_id`, текст из `ToolDefinition.confirm_text`, кнопки `confirm` / `cancel`
   с `payload: {confirm_id}`) и `state_patch.pending_confirmation`
   `{confirm_id, tool, arguments}`. Модель получает «ждёт подтверждения, не повторяй».
2. Ввод `action` с `action_id` `confirm` / `cancel` и `payload.confirm_id` → `TurnContext.confirmation`.
   Агентный цикл обрабатывает его до первого вызова модели: при совпадении с
   `pending_confirmation` подтверждённый вызов исполняется (`ToolExecutor.execute_confirmed`)
   с аргументами из состояния, а не от модели или клиента; отмена ничего не исполняет;
   ожидание снимается. Итог — пометка к сообщению пользователя для модели.
   Несовпадающий или уже снятый `confirm_id` (старое сообщение, двойное нажатие) ничего
   не исполняет — пометка «подтверждение устарело».
3. Подписи кнопок — `assistant.confirm_labels` (по умолчанию в схеме «Подтвердить» / «Отмена»).
4. Заявки хранит новый модуль `leads` (таблица `leads`, репозиторий по `tenant_id`), tools
   видит его через порт `LeadStore`. Поля заявки — строки по полям формы из `forms`
   конфига; та же проверка значений — у `form_submit` (422 до записи ввода).

## Альтернативы
- Модель сама повторяет вызов после «да» пользователя (флаг `confirmed` в аргументах) —
  побочный эффект зависит от модели, аргументы между показом и исполнением могут измениться.
- Подтверждение текстом («да») без кнопки — неоднозначно и не связано с конкретным вызовом.
- Ожидающий вызов в отдельной таблице — лишняя сущность; состояние диалога уже хранится
  и сохраняется вместе с ходом.
- Заявки в модуле chat — смешивает переписку и бизнес-результат; доставка заявок (webhook,
  админка) будет расти отдельно.

## Последствия
- Один ожидающий вызов на диалог: новый запрос подтверждения заменяет прежний, старая кнопка
  становится устаревшей.
- Ход с подтверждением — минимум один вызов модели после исполнения (чтобы ответить
  пользователю); пометка об итоге остаётся только в контексте этого хода, в истории —
  нажатие кнопки, вызов — в `tool_calls`.
- Нет защиты от двух параллельных ходов одного диалога с одним `confirm_id` (оба прочтут
  ожидание до записи) — клиент блокирует ввод на время хода; серверная блокировка хода — P5-07/P7.
- Схема `create_lead.fields` — объединение полей всех форм: условные схемы (`if/then`,
  `allOf` на верхнем уровне) не все провайдеры принимают; принадлежность полей форме
  проверяет `check`.
- Доставка заявок бизнесу (webhook, email, просмотр в админке) — отдельная задача.
