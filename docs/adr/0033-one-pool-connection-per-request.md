# ADR-0033: Запрос не держит два соединения пула — зависимости закрывают транзакцию до хода

- Статус: принято
- Дата: 2026-10-07

## Контекст
P7-05 (нагрузочный тест) нашёл взаимную блокировку пула БД. На запрос есть две сессии
(`shared/api/deps.py`, ключ кэша зависимостей FastAPI учитывает `scope`):

- `DbSession` (`scope="function"`) — закрывается после выхода из эндпоинта; её берёт проверка
  ключа виджета `require_widget_access` (`WidgetTenant`) на всех публичных маршрутах;
- `StreamDbSession` (`scope="request"`) — живёт до конца отправки SSE-ответа.

Проверка ключа читала `widget_keys` и держала соединение (транзакция открыта) до выхода из
эндпоинта, а `start_turn` в эндпоинте хода брал второе соединение через `StreamDbSession`.
При ~15 одновременных ходах (пул 5 + 10) все соединения заняты проверками ключа, каждый ход ждёт
второе — до `pool_timeout` (30 с), затем 500 `internal`; прогон на 50 диалогов не завершался.

Обычные тесты этого не ловят: `db_client` подменяет `get_session` одной сессией на тест,
и `DbSession` и `StreamDbSession` в них — одно соединение.

## Решение
1. **Правило:** запрос в каждый момент держит не больше одного соединения пула. Зависимость,
   которая читает БД до эндпоинта, закрывает свою транзакцию (`commit`), когда данные получены:
   соединение возвращается в пул, сессия остаётся рабочей (следующий запрос возьмёт соединение
   заново).
2. **Сейчас:** `require_widget_access` делает `await session.commit()` после проверки ключа
   и origin. Для эндпоинтов на `DbSession` (создание диалога, история) это та же сессия
   (кэш зависимости): их запись идёт следующей транзакцией; проверка ключа только читает,
   атомарность записи эндпоинта не меняется.
3. **Проверка:** `tests/test_db_pool.py` — приложение с пулом из одного соединения,
   проверка ключа читает БД, эндпоинт пишет через `StreamDbSession`; без правила — таймаут пула.
   Регрессии под нагрузкой — `make loadtest`.
4. **Размер пула** — `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` (по умолчанию 5 / 10).

## Альтернативы
- **Отдельная короткая сессия в проверке ключа** (`async with session_factory()`). Соединение
  отпускается сразу, но зависимость обходит `get_session`: тестовая подмена сессии (транзакция
  с откатом) её не видит, тестам понадобились бы закоммиченные ключи виджета в `app_test`.
- **Одна сессия на запрос** (проверка ключа на `StreamDbSession` в эндпоинтах хода). Убирает
  второе соединение, но ход и так держит своё соединение весь стрим (P7-08), а смешение
  транзакций проверки ключа и хода усложняет `commit` в `TurnStream`; эндпоинты хода и
  остальные маршруты получили бы разные варианты `WidgetTenant`.
- **Только увеличить пул.** Блокировка лишь сдвигается: при `N` одновременных ходах и пуле
  меньше `2N` она та же, а соединения Postgres ограничены (`max_connections`).

## Последствия
- Под нагрузкой ходы стоят в очереди за пулом, а не блокируют друг друга: n=200 по 3 хода —
  0 ошибок (P7-05); потолок процесса на моке модели — CPU (~15 ходов/с).
- Новая зависимость, читающая БД (авторизация админки P8-01, проверки перед ретраем), должна
  закрыть транзакцию до эндпоинта со стримом; иначе — повтор этой блокировки. Тест на пуле
  из одного соединения — образец.
- Ход по-прежнему держит соединение до конца ответа модели (`idle in transaction`), поэтому
  одновременных ходов на процесс не больше размера пула — отдельное решение в P7-08,
  которое этот ADR не предрешает.
