# ADR-0036: Пользователи админки — модуль access, роли по тенантам, сессии в БД

- Статус: принято
- Дата: 2026-10-08

## Контекст
P8-01: админке нужны пользователи, роли и привязка к тенантам. Сейчас `/v1/admin/*` закрыт
одним `ADMIN_API_TOKEN` из env на все тенанты (ADR-0028), и ADR-0028 обещает заменить его в P8-01.

Ограничения:
- По ADR-0006 у каждой бизнес-таблицы есть `tenant_id`. Но пользователь админки (подрядчик,
  сотрудник платформы) может работать в нескольких тенантах.
- Эндпоинты админки будут в разных модулях: журнал хода — `observability` (P7-02), конфиг —
  `tenants` (P8-02), источники — `knowledge` (P8-03), диалоги — `chat` (P8-04). `observability`
  и `shared` находятся ниже остальных модулей и не могут импортировать модуль пользователей.
- Новых зависимостей нет: argon2 и bcrypt недоступны.

## Решение
1. **Модуль `access`** — пользователи админки, роли, сессии, вход и выход. Он стоит в верхнем
   слое рядом с `chat` и может импортировать `tenants`. Use cases админки (конфиг, источники,
   диалоги) остаются в своих модулях: `access` отвечает только за то, кто вошёл и что ему можно.
2. **Таблицы:**
   - `admin_users(id, email, password_hash, is_superadmin, is_active)` — без `tenant_id`.
     Это кросс-тенантный справочник по образцу `tenants` и `SqlTenantDirectory` (ADR-0007),
     работа с ним идёт через `SqlAdminUserDirectory`.
   - `admin_memberships(tenant_id, user_id, role)` — обычная таблица тенанта
     (`TenantRepository`), не больше одной роли на тенант.
3. **Роли:**
   - `viewer` — диалоги и журнал хода;
   - `editor` — то же плюс конфиг агента и источники; старшая роль включает права младшей;
   - `is_superadmin` — все тенанты и управление пользователями.
   Роль хранится как VARCHAR + CHECK, как статусы: новая роль добавляется без ALTER TYPE.
4. **Пароль:** `scrypt` из stdlib (N=2^15, r=8, p=1, соль 16 байт). Параметры хранятся в хэше
   (`scrypt$N$r$p$соль$хэш`), поэтому их можно усилить или перейти на другой алгоритм без
   миграции. Минимальная длина — 12 символов. Email нормализуется (trim, lower) и служит логином.
   - Дополнение (P9-01aa, REVIEW.md: AC-12). Пароль приводится к NFKC, длина считается после
     нормализации. Хэши, созданные до этого, проверяются повторно по строке как есть.
     Повторная проверка стоит второй scrypt, но только для паролей, которые NFKC меняет.
     Убрать её можно, когда у всех пользователей пароль сменён после P9-01aa.
   - Максимум длины — 1024 символа, как у входа: CLI не примет пароль, с которым потом
     нельзя войти.
   - Параметры хэша вне допустимых пределов (подменённый `n`) дают отказ, а не 500.
5. **Пользователей создаёт CLI:** `make admin-user email=… args="--tenant slug=role"`. Пароль
   берётся из `ADMIN_PASSWORD` или вводится с клавиатуры. API управления пользователями — позже.
6. **Сессии (P8-01b):**
   - вход по email и паролю выдаёт непрозрачный токен (256 бит); в `admin_sessions` хранится
     только его sha256 и `expires_at`, как у ключей виджета;
   - клиент передаёт токен в `Authorization: Bearer` (браузер — в HttpOnly-cookie,
     ADR-0044); выход, отключение пользователя или
     истечение срока сразу закрывают доступ;
   - вход ограничен лимитом частоты по IP и email (ADR-0030); для неизвестного email
     считается фиктивный хэш, чтобы по времени ответа нельзя было узнать, есть ли такой email.
     По IP считаются все попытки. По email — только неудачные (P9-01o, REVIEW.md: AC-3):
     до проверки пароля лимит только проверяется (`RateLimiter.check`), а неверный пароль
     учитывается (`hit`). Успешные входы владельца лимит не тратят. Перебор с многих IP
     по-прежнему блокирует email до конца окна. Без Redis оба правила считаются в памяти
     процесса (`local_fallback`, дополнение ADR-0030 в P9-01m).
7. **Проверка доступа из любого модуля (P8-01b):**
   - `shared.kernel` содержит `AdminPrincipal` и порт `AdminAuthenticator`; реализацию даёт
     `access`, подключение — `main.py` через `app.state`;
   - зависимость в `shared.api` проверяет роль в тенанте из пути запроса: 401 — нет сессии,
     403 — нет роли;
   - `ADMIN_API_TOKEN` удаляется без переходного периода: он нигде не используется, а
     суперадмина можно создать через CLI.

7. **Нагрузка и сессии (дополнение P9-01aa, REVIEW.md: AC-4, AC-7, AC-9, AC-10).**
   - **Пул БД.** Вход закрывает транзакцию чтения до проверки пароля: соединение пула не
     занято на время scrypt.
   - **Пул потоков.** Пароли проверяются в своём пуле потоков `KdfPool` (`ADMIN_KDF_THREADS`,
     по умолчанию 2), а не в общем `to_thread`. Флуд входа ждёт в его очереди и не отнимает
     потоки у разбора источников и DNS.
   - **Неизвестный email.** Фиктивный хэш собирается без KDF: случайные соль и ключ с текущими
     параметрами. Проверка по нему стоит один scrypt, как у настоящего пользователя.
   - **Логи входа.** `admin.login_succeeded` — с `user_id`. `admin.login_failed` — с причиной
     (`unknown_user`, `bad_password`, `inactive`) и `email_hash`. Клиенту по-прежнему уходит
     одинаковый 401.
     - `email_hash` — префикс sha256 без соли: email открытым текстом в лог не попадает, но
       это псевдоним, а не анонимизация. По списку известных адресов хэш восстанавливается.
   - **Лимит сессий.** У пользователя не больше `ADMIN_MAX_SESSIONS_PER_USER` (10) сессий.
     - При входе новая сессия остаётся всегда, из прочих закрываются самые старые по времени
       создания. Даже если срок сократили и новая сессия истекает раньше старых.
     - Лимит приблизительный: параллельные входы не видят незакоммиченные сессии друг друга.
   - **Истёкшие сессии.** Сессии всех пользователей удаляет ежедневная чистка воркера
     (ADR-0043) при обходе всех тенантов, а также `make retention` без списка тенантов.
   - **Известные ограничения.**
     - Очередь `KdfPool` не ограничена: при флуде честный вход ждёт за всей очередью. Если
       это станет проблемой, нужен предел очереди с ответом 503.
     - Проверка пароля и создание сессии не атомарны. Вход, начатый со старым паролем до его
       смены, может создать сессию уже после закрытия всех сессий пользователя. Так было и до
       P9-01aa; закрывается версией учётных данных в сессии.

## Альтернативы
- **Пользователи в модуле `tenants`.** Кода меньше, но в `tenants` смешались бы конфиг бизнеса
  и учётные записи людей. `observability` эта схема всё равно не решает: модуль ниже `tenants`,
  порт в `shared` нужен в любом случае.
- **Модуль `admin` со всеми эндпоинтами админки.** Тогда `admin` знал бы внутренности
  конфигов, источников и диалогов, и туда стекалось бы всё «админское». Порт в `shared`
  оставляет use cases в их модулях.
- **`tenant_id` у пользователя (один тенант на пользователя).** Строго по ADR-0006, но подрядчику
  с несколькими тенантами пришлось бы заводить несколько учётных записей с разными паролями.
- **JWT вместо сессий в БД.** Не нужен запрос в БД на проверку, но токен нельзя отозвать до
  истечения при выходе или отключении. Нагрузка админки мала, запрос по индексу дешёвый.
- **argon2id / bcrypt.** Предпочтительнее scrypt по OWASP, но это новая зависимость. Формат
  хэша позволяет перейти на них позже.
- **Оставить `ADMIN_API_TOKEN` как запасной вход.** Это общий ключ ко всем тенантам в env —
  ровно то, что P8-01 должна убрать.

## Последствия
- ADR-0006 уточняется: пользователи админки (как и сами тенанты) — справочник без `tenant_id`.
  Данные тенанта по-прежнему читаются только через репозитории с явным `tenant_id`, а роль
  проверяется по `admin_memberships` этого тенанта.
- Новые эндпоинты админки в любом модуле объявляют нужную роль через зависимость из `shared`
  и не импортируют `access`.
- Роли — догадка до пилота. Вероятно, понадобится роль для управления пользователями своего
  тенанта; добавить её — новое значение в CHECK и в `AdminRole`.
- Нет 2FA, SSO, сброса пароля по почте и аудита действий админов — это отдельные задачи.
