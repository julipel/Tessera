# ADR-0032: Маскирование персональных данных в трейсах — шаблоны контактов и данные форм целиком

- Статус: принято
- Дата: 2026-10-07

## Контекст
P7-03 (ADR-0029) отправляет в Langfuse Cloud полный текст хода: ввод клиента, системный промпт
со слотами и фактами, историю, результаты инструментов, аргументы `create_lead` и ответ. Среди
этого — телефоны, e-mail, Telegram-ники, имена из форм заявок. Langfuse — внешний сервис; до
пилота с реальными клиентами персональные данные туда уходить не должны.

У SDK есть функция `mask`: вызывается синхронно для input, output и metadata каждого
observation до экспорта; сбой функции — заглушка `<fully masked due to failed mask function>`.

## Решение
1. **`observability.domain.pii.mask_pii`** — функция `mask` клиента Langfuse
   (`LangfuseTracer.create`), одна точка для всего, что уходит в Langfuse.
2. **По шаблонам** в любых строках: e-mail → `[email]`, телефон (10–15 цифр с разделителями)
   → `[phone]`, карта (13–19 цифр и контрольная сумма Луна) → `[card]`, `@ник` → `[handle]`.
   Цифры, примыкающие к буквам или дефисам (UUID, артикулы), не трогаются; цены, даты,
   объёмы короче 10 цифр.
3. **По структуре:** значения под ключами `values` (UserInput `form_submit`), `fields`
   (`create_lead`) и `facts` (факты о клиенте: аргументы `update_dialog_state`) — `[скрыто]`
   целиком; у форм ключи остаются (видно, какие поля заполнены), у фактов — их число. Так
   скрываются имена и комментарии, которые шаблонами не поймать. Факты — главное место, куда
   модель складывает сведения о клиенте в свободной форме («Имя: Юлия.»): живая проверка
   показала, что имя чаще приходит текстом в чат, чем формой. Список `facts` в JSON состояния
   диалога внутри текста системного промпта (Runtime-слой) скрывается так же (конец списка —
   по разбору JSON). Строка отправки формы
   в истории для модели («[Отправлена форма …: {json}]») и JSON-строки (аргументы вызовов
   модели) разбираются и маскируются по тем же правилам.
4. Наша БД (сообщения, журнал хода) не маскируется: это хранилище платформы, данные там нужны
   для работы; сроки хранения — отдельно (P8).

## Альтернативы
- **Не отправлять содержимое вовсе** (только модели, токены, время, стоимость) — безопасно, но
  трейсы теряют смысл для разбора диалогов; можно добавить флагом, если понадобится.
- **NER-модель для имён и адресов** — точнее, но тяжёлая зависимость и время на каждый трейс.
- **Маскирование при записи атрибутов в нашем коде** (`TracedLLM`, `traced_turn`) — легко
  пропустить новое место; функция SDK покрывает все observation сразу.
- **Self-hosted Langfuse** — данные остаются у нас, но тяжёлая инфраструктура (ClickHouse,
  MinIO); маскирование нужно и там по принципу минимизации.

## Последствия
- Имена, адреса и другие данные в свободном тексте сообщений клиента («Юлия» в ответ на вопрос
  об имени), в ответе ассистента и в сводке ранней истории уходят в Langfuse как есть —
  известное ограничение; закрывается NER или отказом от содержимого.
- В Langfuse не видно, что модель запомнила о клиенте (только число фактов); для разбора — журнал
  хода в нашей БД (`state_updated`, ADR-0028).
- Номера заказов из 10–15 цифр маскируются как телефоны — допустимо.
- Новые формы и инструменты с персональными данными должны класть их под `values`/`fields`
  или добавлять ключ в `_FORM_KEYS`.
