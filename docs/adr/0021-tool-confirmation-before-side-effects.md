# ADR-0021: Подтверждение побочных эффектов — ожидающий вызов в состоянии, исполнение без модели

- Статус: предложено
- Дата: 2026-10-05

## Контекст
P5-04: `ToolDefinition.requires_confirmation` и компонент `confirm` были в контрактах, но
не работали. Первый такой инструмент — `create_lead` (заявка на консультацию). Побочный
эффект (заявка, бронь) нельзя доверять модели: она может создать его без согласия
пользователя, повторить или исказить аргументы после «да». По ADR-0004 UI — от бэкенда,
по ADR-0020 язык кнопок — в конфиге тенанта, не в ядре.

## Решение
1. Tool Registry не исполняет вызов инструмента с `requires_confirmation`: после проверки
   аргументов (JSON Schema и `ToolDefinition.check`) возвращает компонент `confirm`
   (`confirm_id`, текст из `ToolDefinition.confirm_text`, кнопки `confirm` / `cancel`
   с `payload: {confirm_id}`) и `state_patch.pending_confirmation`
   `{confirm_id, tool, arguments}`. Модель получает «ждёт подтверждения, не повторяй».
2. Ввод `action` с `action_id` `confirm` / `cancel` и `payload.confirm_id` → `TurnContext.confirmation`.
   Агентный цикл обрабатывает его до первого вызова модели: при совпадении с
   `pending_confirmation` подтверждённый вызов исполняется (`ToolExecutor.execute_confirmed`)
   с аргументами из состояния, а не от модели или клиента; отмена ничего не исполняет;
   ожидание снимается. Итог — пометка к сообщению пользователя для модели.
   Несовпадающий или уже снятый `confirm_id` (старое сообщение, двойное нажатие) ничего
   не исполняет — пометка «подтверждение устарело».
3. Подписи кнопок — `assistant.confirm_labels` (по умолчанию в схеме «Подтвердить» / «Отмена»).
4. Заявки хранит новый модуль `leads` (таблица `leads`, репозиторий по `tenant_id`), tools
   видит его через порт `LeadStore`. Поля заявки — строки по полям формы из `forms`
   конфига; та же проверка значений — у `form_submit` (422 до записи ввода).
   Ключ идемпотентности заявки — `confirm_id` (P9-01g): реестр передаёт его обработчику
   в `ToolContext.confirm_id`, `LeadStore.create(..., idempotency_key)` вставляет заявку
   через `ON CONFLICT DO NOTHING` по `(tenant_id, conversation_id, idempotency_key)`, повтор
   возвращает id уже созданной.

## Альтернативы
- Модель сама повторяет вызов после «да» пользователя (флаг `confirmed` в аргументах) —
  побочный эффект зависит от модели, аргументы между показом и исполнением могут измениться.
- Подтверждение текстом («да») без кнопки — неоднозначно и не связано с конкретным вызовом.
- Ожидающий вызов в отдельной таблице — лишняя сущность; состояние диалога уже хранится
  и сохраняется вместе с ходом.
- Заявки в модуле chat — смешивает переписку и бизнес-результат; доставка заявок (webhook,
  админка) будет расти отдельно.

## Последствия
- Один ожидающий вызов на диалог: новый запрос подтверждения заменяет прежний, старая кнопка
  становится устаревшей.
- Ход с подтверждением — минимум один вызов модели после исполнения (чтобы ответить
  пользователю); пометка об итоге остаётся только в контексте этого хода, в истории —
  нажатие кнопки, вызов — в `tool_calls`.
- Два параллельных хода с одним `confirm_id` исполняют действие один раз: ожидание
  снимается условным UPDATE до начала хода, и в диалоге идёт один ход (ADR-0041). Если
  исполнение всё же повторится, уникальный индекс `leads` не даст второй заявки.
- Сбой инструмента с побочным эффектом (таймаут, исключение) — `retryable: false`: действие
  могло выполниться, модель не вызывает инструмент повторно.
- Схема `create_lead.fields` — объединение полей всех форм: условные схемы (`if/then`,
  `allOf` на верхнем уровне) не все провайдеры принимают; принадлежность полей форме
  проверяет `check`.
- Доставка заявок бизнесу (webhook, email, просмотр в админке) — отдельная задача.

## Дополнение (P9-01ad, 2026-10-16): срок жизни ожидающего вызова

Проигнорированная кнопка оставалась рабочей бесконечно: через несколько дней нажатие исполнило
бы устаревшие аргументы (REVIEW.md: M-4).

- `PendingConfirmation.created_at` (UTC, в JSON — ISO 8601 с поясом) ставит Registry
  при показе подтверждения (часы — параметр `now`).
- Срок жизни — `CONFIRMATION_TTL = 1 час`, константа в `memory`, не настройка тенанта:
  кнопка — часть текущего разговора, а переспросить после часа дешевле, чем исполнить
  устаревшее.
- Просроченное ожидание снимает `LoopTurnAgent` в начале хода (часы хода, лог
  `confirmation_expired`): событие `DialogStateUpdated` первым, состояние без ожидания
  пишется в конце хода, даже если инструменты его не меняли — как починка битого
  состояния (M-3). Нажатие просроченной кнопки получает пометку «подтверждение устарело»
  (действие не выполнено), модель предлагает оформить заново.
- Ожидание без `created_at` (сохранено до P9-01ad) — просроченное: его возраст неизвестен.
  Битый `created_at` (не строка, не ISO, без пояса) — повреждённое ожидание (M-3), снимается.
- Срок проверяется в начале хода, без фоновой чистки: в БД просроченное ожидание лежит до
  следующего хода, но ничего не исполнит.
- `created_at` без пояса в конструкторе — `ValueError`; из будущего больше чем на минуту
  (сбитые часы) — просрочено, срок не продлевается. Часы `builtin_turn_agent(now=…)` общие
  для Registry и проверки срока.
- Ограничение: снятие просроченного ожидания пишется безусловно (`keep_pending_confirmation`
  не сохраняет ожидание, раз ход его изменил). Если параллельный ход, прочитавший состояние
  позже, успел поставить новое ожидание, оно затрётся — отказ безопасный: его кнопка ответит
  «устарело», двойного исполнения нет. Один ход на диалог (ADR-0041) делает это редкостью.

Отвергнуто: срок в ходах (K ходов без нажатия) — пользователь может задать вопрос и только
потом нажать «Да»; настройка `limits.confirmation_ttl_s` — меняет контракт AgentConfig без
понятной потребности тенантов.

## Дополнение (P9-01ai, 2026-10-17): одно подтверждение за ход

Два вызова с подтверждением в одном ходе (параллельно в шаге или на разных шагах) оставляли
действующим последний: кнопка первого, уже показанная клиенту, сразу «устаревала»
(REVIEW.md: AG-12).

- В ходе действует первый запрос подтверждения. Следующие получают ошибку `forbidden` без
  компонента и без `pending_confirmation`: «уже показано подтверждение другого действия;
  предложи его после ответа пользователя». Это не ошибка аргументов, поэтому ретраи хода
  (`max_tool_retries`) на отказ не тратятся.
- Внутри шага правило применяет `ToolRegistry.execute_many`, между шагами — цикл агента.
  Обработчики до подтверждения не исполняются, поэтому отказ без побочных эффектов.
- Между ходами правило «новый запрос заменяет прежний» остаётся: клиент ушёл от прошлой
  кнопки к новому разговору.
