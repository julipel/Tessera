# ADR-0006: Изоляция тенантов на уровне репозитория, без RLS в Postgres

- Статус: принято
- Дата: 2026-10-02

## Контекст
Платформа мультитенантная: все компании живут в одной БД, в одной схеме. Утечка данных
одного тенанта другому (каталог, диалоги, лиды) — самый тяжёлый класс ошибок. Код во многом
пишет AI-агент, который может забыть фильтр в очередном запросе. Нужен механизм, который
делает правильный путь простым, а ошибку — заметной на тестах. При этом нужны async
SQLAlchemy, пул соединений, фоновые задачи arq и транзакционные тестовые фикстуры.

## Решение
Изоляция обеспечивается в коде приложения, на уровне репозиториев (реализовано в P1-04):
- Каждая бизнес-таблица наследует `TenantScopedBase` (`shared`): `tenant_id UUID NOT NULL`
  с индексом.
- Доступ к данным только через наследников `TenantRepository[Model]`. Все методы принимают
  `tenant_id: TenantId` первым обязательным аргументом. Запросы строятся через единственный
  `_scoped(tenant_id)`, который добавляет фильтр. `add` отклоняет объект с чужим `tenant_id`.
- `TenantId` — отдельный тип (`NewType`), mypy strict не даёт подставить произвольный UUID
  без явного приведения.
- Специфичные запросы репозиториев-наследников строятся поверх `_scoped`, а не `select(...)`
  с нуля.
- Тест изоляции для каждого репозитория: данные тенанта B не видны и не изменяются из-под
  тенанта A (`get`, `list`, `delete`).
- Тот же принцип для Qdrant: `tenant_id` в payload и обязательный фильтр в порте поиска (P4-06).

## Альтернативы
- **Postgres Row-Level Security** (`SET app.tenant_id` + политики). Защита на уровне БД,
  но: переменная сессии плохо сочетается с пулом соединений и async (нужен `SET LOCAL` в
  каждой транзакции, риск утечки контекста между запросами); владелец таблиц и суперпользователь
  обходят RLS без `FORCE`; миграции, воркеры и админские отчёты по нескольким тенантам требуют
  отдельных ролей; ошибки проявляются как «пустой результат», а не как исключение. Не исключаем
  как второй рубеж позже — отдельным ADR.
- **Схема или БД на тенанта.** Сильная изоляция, но миграции × N тенантов, сложный пул,
  дорогие кросс-тенантные отчёты и эвалы. Избыточно для текущего масштаба.
- **Глобальный фильтр через события ORM** (`do_orm_execute` + `with_loader_criteria` по
  contextvar). Неявный: тенант берётся из контекста, его легко потерять в фоновых задачах и
  тестах, а код, читающий данные, не показывает, к какому тенанту он обращается. Противоречит
  правилу «репозитории принимают `tenant_id` явно» (CLAUDE.md, architecture.md §10).

## Последствия
- Изоляция видна в сигнатурах и проверяется тестами; не нужны роли БД и переменные сессии.
- Защита держится на дисциплине: прямой `select` в обход репозитория технически возможен.
  Смягчение — ревью (сабагент reviewer), тесты изоляции, возможная статическая проверка
  `select(` вне `infrastructure/` в будущем.
- Ошибка в одном репозитории не перехватывается БД — поэтому тест изоляции обязателен
  для каждого нового репозитория (часть DoD задач с таблицами).
- Кросс-тенантные операции (админка платформы, миграции данных) делаются отдельными явными
  сервисами, а не через `TenantRepository`.
- Не противоречит ADR-0001–0005; ничего не заменяет.
