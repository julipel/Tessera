# ADR-0035: Отмена хода из любого процесса API — каталог ходов и pub/sub в Redis

- Статус: принято
- Дата: 2026-10-08

## Контекст
Явная отмена (`POST .../turns/{turn_id}/cancel`) прерывает агента через `TurnRegistry`, а он
хранит ходы в памяти процесса. Если у API несколько процессов (воркеры uvicorn, реплики при
деплое P9), запрос отмены может попасть не в тот процесс, где идёт стрим. Тогда сервер
отвечает 404, фронт (`useChat.stopTurn`) понимает это как «ход уже закончился», и кнопка
«Остановить» ничего не делает. На стенде с двумя воркерами отмена не сработала в 8 случаях
из 12.

Обрыв соединения этой проблемы не имеет: его видит процесс со стримом. Redis в проекте уже есть
(лимиты, ADR-0030), и все процессы API к нему подключены.

## Решение
1. **Каталог ходов** — порт `chat.domain.ports.TurnDirectory`, реализация
   `RedisTurnDirectory`:
   - пока ход идёт, в Redis лежит ключ `turn:<turn_id>` = `<tenant_id>:<conversation_id>`
     (`SET ... EX 900`); `TurnRegistry.add`/`remove` ставят и снимают его. TTL нужен на случай
     падения процесса до снятия ключа;
   - отмена хода, которого нет в процессе: ключ читается и сверяется с тенантом и диалогом
     из запроса. Ключа нет или он чужой — `False` (404). Иначе turn_id публикуется в канал
     `turns:cancel` (`PUBLISH`), ответ — 204.
2. **Подписка.** Каждый процесс в lifespan запускает задачу `RedisTurnDirectory.listen`: она
   подписана на `turns:cancel` и вызывает `TurnRegistry.cancel_local`. Тот отменяет ход, если
   ход в этом процессе, иначе ничего не делает. У подписки свой клиент Redis без таймаута
   чтения (у основного 0,5 с — для лимитов); читает она `get_message(timeout=1.0)`, чтобы
   проходили health check. При сбое Redis задача переподключается раз в секунду.
3. **Ход в этом процессе** отменяется как раньше, без Redis. При одном процессе Redis
   на отмену не нужен.
4. **Redis недоступен** — как у лимитов: `warning` в лог (`turn_directory_unavailable`,
   `turn_cancel_listener_failed`), ход идёт, отмена работает только в процессе со стримом.
5. **Контракт не меняется**: 204 — отмена принята, стрим закончится `done{interrupted}`;
   404 — хода нет, он завершён или чужой.
6. **Тесты:** `InMemoryTurnDirectory` (несколько реестров на одном каталоге — несколько
   процессов), тесты на настоящем Redis и с недоступным Redis — `tests/test_turn_directory.py`.
   В остальных тестах реестр только локальный (`conftest.app`).

## Альтернативы
- **Ход сам опрашивает Redis** (ключ `turn_cancel:<id>` раз в N мс в `TurnStream`). Подписка
  не нужна, но отмена приходит с задержкой до N мс, и каждый ход опрашивает Redis постоянно,
  даже когда отмены нет.
- **Привязка диалога к процессу на балансировщике** (sticky sessions по `conversation_id`).
  Кода не требует, но отмена зависит от настройки инфраструктуры. Процесс воркера uvicorn
  балансировщик не выбирает (сокет общий), а при перезапуске реплики привязка теряется.
- **Redis Streams или очередь arq.** Сообщения хранятся, есть подтверждение доставки. Но отмена
  нужна только живому ходу: если процесса уже нет, доставлять некому, и хранить сообщение
  незачем. Pub/sub проще, а потерянное сообщение означает то же, что ход уже завершён.

## Последствия
- «Остановить» работает при любом числе процессов API: на стенде с двумя воркерами 12 отмен
  из 12, 2 из них переданы через Redis.
- На каждый ход — два запроса к Redis (`SET`, `DEL`). Если Redis недоступен, начало хода
  ждёт до таймаута соединения (0,5 с), как и проверка лимитов.
- 204 означает, что отмена передана, а не что ход уже прерван. Если ход закончился между
  проверкой ключа и доставкой сообщения, стрим кончится обычным `done`. Это та же гонка,
  что и при отмене в одном процессе.
- Ход длиннее TTL ключа (15 мин) после истечения ключа отменяется только из своего процесса.
- Продолжение стрима после перезагрузки страницы (буфер событий, `Last-Event-ID`) здесь
  не решается — P7-06b, по метрикам пилота. Каталог ходов там пригодится: он показывает,
  что ход ещё идёт.
