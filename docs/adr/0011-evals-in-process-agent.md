# ADR-0011: Эвалы гоняют агента in-process, конфиг тенанта — из YAML

- Статус: предложено
- Дата: 2026-10-03

## Контекст
P3-01 вводит `make eval`: 20 эталонных диалогов из `evals/dialogs/*.yaml` проигрываются через
агента, результат каждого хода проверяется по ожиданиям (`evals/README.md`). Для проверок на
каждом ходе нужны текст ответа, имена вызванных инструментов, типы UI-компонентов и
DialogState после хода.

Эвалы измеряют качество диалога: промпт, конфиг тенанта, описания инструментов, поведение
модели. Транспорт и хранение (SSE, идемпотентность, запись сообщений и ToolCall) покрыты
интеграционными тестами chat (P1-08, P2-08). Эвалы запускают на каждую правку промпта или
конфига (`prompt-engineer`, P6), поэтому важно, чтобы запуск был быстрым и не требовал лишней
подготовки.

Ограничения:
- через HTTP API состояние диалога наружу не отдаётся, а сырые результаты инструментов в SSE
  не попадают (contracts.md §2);
- если брать конфиг из БД, перед каждым прогоном нужен `make seed`, а в базе копятся
  эвал-диалоги;
- эвал обязан идти тем же путём сборки хода, что и прод: сборка промпта, преобразование
  `action`/`form_submit` в текст для модели, набор встроенных инструментов. Иначе эвал
  проверяет не то, что работает у пользователя.

## Решение
1. Раннер (`apps/api/evals/`, вне пакета `app`, в wheel не входит) поднимает агента в своём
   процессе, без HTTP-слоя. Ход выполняет тот же `LoopTurnAgent`, что использует chat API;
   инструменты собираются так же, как в `get_turn_agent`. Для этого `chat/public.py`
   экспортирует `LoopTurnAgent`, `TurnRequest`, `ChatMessage`, `MessageRole`, `MessageStatus`.
   Раннер, как и любой другой код, импортирует модули только через `public.py`/`kernel.py`
   (ADR-0001, ADR-0008).
2. AgentConfig берётся из `config/tenants/<tenant>.yaml` (`load_tenant_spec`). Это тот же
   файл, из которого делает seed `make seed`, поэтому эвал проверяет рабочую копию конфига
   ещё до публикации версии. Поле `tenant` в диалоге — это slug тенанта.
3. История, DialogState и показанные компоненты хранятся в памяти раннера, поверх ходов:
   состояние берётся из `DialogStateUpdated`, компоненты — из `ComponentEmitted`, вызовы —
   из `ToolStarted`/`ToolFinished`.
4. LLM-клиенты собираются из `Settings` через `LLMClients`, как в `create_app`. Ключи берутся
   только из env.
5. Пока инструменты не ходят в БД, `tenant_id` эвал-хода — фиксированный id для каждого slug.
   Когда появятся инструменты знаний и каталога (P4), им понадобятся данные тенанта. Тогда
   раннер будет брать `tenant_id` из БД по slug и открывать сессию для инструментов, но конфиг
   по-прежнему возьмёт из YAML и диалоги в БД записывать не будет. Это изменение — часть P4-07/
   P4-08, нового ADR не требует.

## Альтернативы
- **Через HTTP API в процессе (ASGI-транспорт, ключ виджета, реальная БД).** Это самый полный
  end-to-end. Но для него нужны Docker, миграции и seed. DialogState и результаты инструментов
  наружу не видны: пришлось бы читать БД в обход API или расширять публичный контракт
  отладочными данными. Эвал-диалоги засоряют базу. Транспорт эвалы не проверяют, а за это
  пришлось бы платить сложностью и временем каждого прогона.
- **Собирать `AgentLoop` прямо из `agent.public`, без chat.** Тогда chat не трогаем, но
  дублируются сборка `TurnContext` и преобразование пользовательского ввода в текст
  (`to_llm_messages`). Две копии разойдутся, и эвал начнёт оценивать не прод-поведение.
- **Конфиг — активная версия из БД.** Так проверяется ровно то, что видят пользователи. Но
  каждый цикл «правка промпта → эвал» требует seed, и новые версии конфига плодятся ради
  экспериментов. Прогон опубликованной версии можно добавить позже флагом, если понадобится
  (P8, админка с версиями).

## Последствия
- `make eval` работает без Docker, пока инструменты не требуют БД (до P4). Нужны только ключи
  провайдера.
- Публичный интерфейс chat расширяется: `LoopTurnAgent` и типы запроса хода становятся частью
  `public.py`. Менять их сигнатуры теперь нужно с оглядкой на раннер эвалов.
- Эвалы не ловят ошибки транспорта и хранения (SSE, запись истории, восстановление состояния
  из БД между ходами). Это по-прежнему задача интеграционных и Playwright-тестов.
- Новое правило: раннер эвалов не содержит своей логики сборки хода. Если для эвала нужно
  поведение, которого нет у `LoopTurnAgent`, оно добавляется в chat/agent, а не в `evals/`.
- import-linter код вне `app` не проверяет. Правило «только `public.py`» для `evals/`
  соблюдается на ревью.
