# ADR-0044: Сессия админки в HttpOnly-cookie

- Статус: принято
- Дата: 2026-10-16
- Дополняет ADR-0036 (как клиент передаёт токен сессии)

## Контекст
Вход в админку отдаёт токен сессии в теле ответа (ADR-0036). Фронт держит его в
`localStorage` и шлёт в `Authorization: Bearer` (REVIEW.md: AC-5). По ADR-0040 домен
один: чат, виджет, демо-витрины и админка живут на одном origin. Поэтому любая XSS на
домене (витрина с inline-скриптом, будущий markdown в чате) читает токен из `localStorage`.
Токен суперадмина даёт доступ ко всем тенантам на 12 часов, с любой машины.

Готовой XSS не найдено, это защита в глубину. CSP и заголовки безопасности — отдельная
задача (P9-01v).

## Решение
1. **Токен — в cookie, недоступной скрипту.** Вход ставит cookie `tessera_admin`:
   - `HttpOnly` — `document.cookie` и `localStorage` её не видят;
   - `Secure` — только HTTPS (`ADMIN_COOKIE_SECURE=false` — для разработки по http не с
     localhost; localhost браузеры и так считают безопасным);
   - `SameSite=Strict` — браузер не отправит её с чужого сайта;
   - `Path=/v1/admin` — уходит только в API админки;
   - `Max-Age` — срок сессии (`ADMIN_SESSION_TTL_HOURS`).

   Срок cookie — до `expires_at` сессии. Выход закрывает сессию и стирает cookie, в том
   числе когда сессия уже истекла (204: устаревшая cookie не остаётся в браузере). Повторный
   вход закрывает прежнюю сессию из cookie. Выход, который не удался (сеть, 5xx), фронт
   показывает ошибкой, а не молча уводит на вход: cookie жива, и на общем компьютере админка
   открылась бы снова без пароля. Фронт токен не хранит вовсе. Есть ли сессия,
   знает только сервер, поэтому страница админки начинает с `GET /v1/admin/me` (401 — на
   вход). Запросы идут с `credentials: "include"`, в CORS включён `allow_credentials`
   (origin перечислены явно).
2. **Bearer остаётся.** `require_admin` берёт токен из `Authorization: Bearer`, а если его
   нет — из cookie. Токен в теле ответа на вход сохраняется для Bearer-клиентов (CLI,
   тесты, будущие интеграции); браузерный фронт его не читает. JSON-схемы не меняются;
   HTTP-поведение меняется: Set-Cookie, 403 на входе с чужим Origin и CSRF-403, повторный
   выход — 204 вместо 401 (contracts.md §7).
3. **CSRF.** Запрос по cookie с POST/PUT/DELETE принимается, только если `Origin` есть в
   `CORS_ORIGINS`, иначе 403 `forbidden`. `SameSite=Strict` отсекает чужие сайты, проверка
   `Origin` — соседние origin того же сайта (другой порт, поддомен). Браузер всегда шлёт
   `Origin` у fetch с такими методами, поэтому запрос без заголовка — тоже отказ. Bearer
   браузер сам не подставляет: запросы с ним `Origin` не проверяют.
   - Вход с `Origin` не из списка — тоже 403 (login CSRF: чужая страница подсунула бы
     браузеру свою сессию). Без `Origin` (CLI) вход разрешён.
   - `CORS_ORIGINS` теперь не только CORS и платформенные origin виджета (ADR-0022), но и
     origin админки: добавить origin «для виджета» — значит доверить ему записи админки по
     cookie. Значения сравниваются точно: «*», путь и слэш в конце отклоняются при старте
     (со «*» и credentials Starlette разрешил бы любому origin читать ответы админки).
4. **Демо через два туннеля** (`make demo-public`, разные `*.trycloudflare.com`) — это
   разные сайты: cookie `SameSite=Strict` с web-страницы в API не уйдёт. Админку в демо не
   показываем, ссылку убираем; админка — локально или после выкладки (P9-01b), где по
   ADR-0040 один origin.

5. **Разработка.** Web и API должны быть одним сайтом: `localhost:3000` и `localhost:8000`
   подходят, `localhost:3000` с API на `127.0.0.1:8000` — нет (разные сайты, cookie
   `SameSite=Strict` не уйдёт). Safari может не принимать `Secure`-cookie по
   `http://localhost` — тогда `ADMIN_COOKIE_SECURE=false` или Chromium/Firefox.

## Альтернативы
- **Токен в памяти страницы** (без хранилища). Перезагрузка выбрасывает из админки, а XSS
  всё равно читает токен из памяти.
- **`SameSite=None` для демо.** Тогда CSRF держится на одной проверке `Origin`, а Safari и
  блокировка сторонних cookie в Chrome такие cookie всё равно не отправят.
- **Один туннель с прокси `/v1/*` через Next.** Демо стало бы одним origin, как прод, но
  прокси нужно проверять на SSE-стриме и с IP посетителя для лимитов (X-Forwarded-For).
  Ради демо — лишняя сложность.

## Последствия
- XSS на домене больше не уводит токен админки. Действовать от имени админа скрипт
  по-прежнему может, пока страница открыта; это закрывает CSP (P9-01v).
- Разработка по http не с localhost (например, по LAN IP) требует
  `ADMIN_COOKIE_SECURE=false`.
- Новые клиенты API админки из браузера обязаны слать `credentials: "include"` и
  выполняться на origin из `CORS_ORIGINS`.
