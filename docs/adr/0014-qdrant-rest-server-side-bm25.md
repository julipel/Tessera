# ADR-0014: Векторный индекс: Qdrant через REST без SDK, BM25 на стороне Qdrant, dense — OpenAI Embeddings

- Статус: предложено
- Дата: 2026-10-04

## Контекст
P4-06 кладёт чанки знаний в Qdrant для гибридного поиска (architecture.md §8, ADR-0003):
dense-вектор и sparse BM25, изоляция тенантов по payload `tenant_id` (ADR-0006). Поиск
(P4-07) пойдёт по тем же векторам, поэтому решения о том, как считаются векторы, должны быть
общими для записи и запроса.

Ограничения:
- `qdrant-client` и библиотек sparse-эмбеддингов (fastembed) нет в зависимостях; новые
  зависимости добавляются только по явному запросу (CLAUDE.md). `fastembed` тянет
  onnxruntime и скачивание моделей в рантайме, `qdrant-client` — grpcio, numpy и др.
- Корпус в основном русскоязычный: BM25 без стемминга плохо сопоставляет формы слов
  («доставка» / «доставкой»).
- IDF должен считаться по коллекции, а не на клиенте: чанки пишутся поэлементно из разных
  синхронизаций, глобальной статистики корпуса у пайплайна нет.
- Нужна операция «точки документа становятся ровно этим набором», устойчивая к откатам
  Postgres (id документа при откате может смениться).
- В локальном окружении Qdrant v1.19.1 (docker-compose); `httpx` и `openai` уже есть.

## Решение
1. **Qdrant — через REST API на `httpx`**, тонкий адаптер `QdrantChunkIndex`
   (`knowledge/infrastructure/qdrant_index.py`) за портом `ChunkIndex` в domain. Нужны
   четыре операции: создать/проверить коллекцию и индексы payload, upsert точек, удаление
   по фильтру. SDK не используется.
2. **Sparse BM25 считает сам Qdrant**: серверный инференс `"model": "qdrant/bm25"` по тексту
   чанка, sparse-вектор `bm25` с модификатором `idf`. Параметры обработки текста — константа
   `BM25_OPTIONS`: snowball-стеммер `russian`, стоп-слова `russian` + `english`,
   `avg_len: 300`. Запросы (P4-07) обязаны передавать те же `BM25_OPTIONS`.
3. **Dense — порт `Embedder`, реализация `OpenAIEmbedder`** (OpenAI Embeddings API через
   SDK `openai`, ключ и `base_url` — `OPENAI_*`, т.е. подходит и совместимый сервер).
   По умолчанию `text-embedding-3-small`, 1536, cosine. Параметр `dimensions` в API не
   передаётся; размерность ответа сверяется с `EMBEDDING_DIMENSIONS`.
4. **Коллекция одна на окружение** (`QDRANT_COLLECTION`): векторы `dense` + `bm25`, индекс
   payload `tenant_id` с `is_tenant: true`, `source_id`, `external_id`; HNSW по тенантам
   (`payload_m: 16`, `m: 0`) без общего графа — поиск без фильтра по тенанту не
   поддерживается. `ensure_collection` идемпотентна и падает на несовместимой коллекции.
5. **Точка = чанк**: id = `Chunk.id`, payload `tenant_id, source_id, document_id,
   external_id, title, url, section, ord, text`. Документ в индексе адресуется
   (`tenant_id`, `source_id`, `external_id`); замена — upsert новых точек, затем удаление
   остальных точек документа (`must_not: has_id`). Каждый фильтр начинается с `tenant_id`.

## Альтернативы
- **`qdrant-client` (async).** Типизированные модели запросов, gRPC, готовые хелперы
  гибридного поиска. Отказались: новая тяжёлая зависимость ради четырёх-пяти вызовов,
  модели SDK протекали бы в адаптер; REST-контракт Qdrant стабилен и проверяется
  интеграционными тестами на реальном Qdrant. Вернуться к SDK можно заменой одного адаптера.
- **Sparse-векторы на клиенте** — fastembed (`Qdrant/bm25`, SPLADE) или свой токенайзер с
  хэшированием термов и TF-весами (IDF — модификатором коллекции). fastembed — тяжёлая
  зависимость с моделями в рантайме; свой токенайзер — собственный стемминг и стоп-слова
  для русского, которые пришлось бы поддерживать. Серверный BM25 даёт стемминг из коробки и
  одинаковую обработку текста на записи и запросе без кода у нас.
- **Полнотекстовый индекс payload в Qdrant** (`type: text`) или **Postgres FTS** вместо
  sparse-векторов. Полнотекстовый фильтр Qdrant не ранжирует (только match), а значит не
  встраивается в RRF; Postgres FTS — второй поисковый контур со слиянием результатов
  между хранилищами вне Qdrant. Противоречит гибридному поиску в Qdrant (ADR-0003, §8).
- **Локальная модель эмбеддингов** (sentence-transformers / ONNX в воркере). Нет
  сетевой зависимости и платы за токены, но тянет torch/onnxruntime и требует ресурсов
  воркера; при необходимости подключается за тем же портом `Embedder` или через
  OpenAI-совместимый сервер (`OPENAI_BASE_URL`) без изменения кода.

## Последствия
- Новых зависимостей нет; адаптеры заменяемы за портами `Embedder` / `ChunkIndex`.
- Стемминг и IDF — ответственность Qdrant: поведение BM25 зависит от версии Qdrant
  (серверный инференс `qdrant/bm25` проверен на v1.19.1; `language` в опциях устарел в 1.19,
  поэтому стеммер и стоп-слова заданы явно). Обновление образа Qdrant — с прогоном
  интеграционных тестов индекса.
- Смена `BM25_OPTIONS`, модели эмбеддингов или размерности требует новой коллекции и
  переиндексации (отдельной команды пока нет). Запись и запрос обязаны брать опции из одной
  константы.
- IDF по умолчанию считается по всей коллекции (всем тенантам): частотность термов одного
  тенанта влияет на ранжирование другого (утечки данных нет — только веса). P4-07 может
  ограничить статистику тенантом (`params.idf.corpus`).
- Индексация зависит от внешнего API эмбеддингов: без ключа или при его недоступности
  документы не индексируются (P4-06b — ошибка элемента синхронизации).
- Текст чанка дублируется в payload Qdrant (источник истины — Postgres): поиск отдаёт
  фрагменты без join в Postgres ценой места в Qdrant.
- Тесты индекса требуют запущенного Qdrant (`make up`), как тесты БД — Postgres.
- Согласуется с ADR-0001 (domain без SDK), ADR-0003 (гибридный поиск текстов в Qdrant),
  ADR-0006 (обязательный фильтр `tenant_id` в порте индекса), ADR-0010 (Embeddings — отдельный
  endpoint OpenAI, адаптер LLM не затрагивается). Ничего не заменяет.
