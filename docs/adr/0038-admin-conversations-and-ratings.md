# ADR-0038: Диалоги в админке — список, разбор хода, оценка ответа сотрудником

- Статус: принято
- Дата: 2026-10-11

## Контекст
P8-04: в админке нужно видеть диалоги тенанта, разбирать ход по шагам (AgentEvent) и
оценивать ответы. Сейчас есть:
- журнал хода `GET /v1/admin/tenants/{id}/events` (ADR-0028), роль `viewer` (ADR-0036);
  `turn_finished.message_id` связывает ход с ответом ассистента;
- публичная история диалога (`GET /v1/conversations/{id}/messages`) — для виджета: без
  заменённых ответов (ADR-0023), без ToolCall-ов, по ключу виджета;
- ADR-0036 отдаёт роли `viewer` «диалоги и журнал», эндпоинты диалогов — модулю `chat`.

Термин «оценка ответа» в roadmap не определён: это может быть оценка посетителем в виджете
или разбор сотрудником. Цель оценки — материал для качества (P6-03, эталоны evals в P9-02).

## Решение
1. **Оценку ставит сотрудник в админке**, роль `viewer`: разбор диалогов — работа ревьюера,
   конфиг и источники ему для этого не нужны. Оценка — `good`/`bad` и необязательный
   комментарий (≤ 2000 символов), только у сообщений ассистента.
2. **Таблица `message_ratings`** в модуле `chat` (рядом с `messages`):
   `(id, tenant_id, conversation_id, message_id, rating, comment, rated_by, rated_by_email,
   created_at, updated_at)`; `message_id` — FK с CASCADE и уникален: **одна оценка на
   сообщение**, повторная перезаписывает её и автора (upsert). `rated_by` — FK на
   `admin_users` с `ON DELETE SET NULL`, `rated_by_email` — email автора на момент оценки:
   `chat` не импортирует `access`, а оценка переживает удаление пользователя.
   `conversation_id` дублирует связь через `messages` — счётчики и фильтр списка без join.
   `rating` — VARCHAR + CHECK, как статусы. Доступ — через хранилище с явным `tenant_id`.
3. **API** (`chat/api/admin_router.py`, contracts.md §7, `admin_conversations.schema.json`):
   - `GET …/conversations` — от новых к старым, keyset-пагинация по `(created_at, id)`
     (`before` — непрозрачный курсор из ответа), фильтр `rating=good|bad` (есть хотя бы одна
     такая оценка), в строке — превью первого ввода клиента и счётчики оценок;
   - `GET …/conversations/{id}` — состояние, сводка и **все** сообщения, включая заменённые
     при повторе (`replaced_by`), со статусом, ошибкой, ToolCall-ами (аргументы, результат,
     ошибка, длительность) и оценкой;
   - `PUT`/`DELETE …/conversations/{id}/messages/{message_id}/rating`.
4. **Ход по шагам** админка берёт из существующего журнала (`events?conversation_id=…`)
   и группирует по `turn_id`; журнал и его контракт не меняются.

## Альтернативы
- **Оценка посетителем в виджете (👍/👎 под ответом).** Даёт голос клиента, но это публичный
  контракт виджета, лимиты частоты, защита от накрутки и UI в чате — отдельная задача; для
  разбора качества нужен взгляд сотрудника, знающего правильный ответ. Таблица допускает
  добавить позже источник оценки (`source`) без смены смысла.
- **Несколько оценок на сообщение (по одной на сотрудника).** Полезно для согласования
  разметки, но на пилоте ревьюеров один-два; усложняет счётчики и UI. При необходимости —
  уникальность `(message_id, rated_by)` новой миграцией.
- **Оценки в `observability` рядом с журналом.** Журнал — неизменяемые события хода, а оценка —
  изменяемая пометка сообщения; FK на `messages` и вывод в деталях диалога естественнее в `chat`.
- **Пагинация смещением (`offset`).** Проще, но при новых диалогах во время просмотра строки
  съезжают и дублируются; на больших тенантах `OFFSET` медленный.

## Последствия
- `chat` получает админский роутер; таблица `message_ratings` ссылается на `admin_users`
  (модуль `access`) только на уровне БД, кода `access` `chat` не импортирует — автор берётся
  из `AdminPrincipal` (`shared.kernel`).
- Админка показывает ПДн диалогов целиком (как и журнал) — маскирование для `viewer` не
  делается; доступ ограничен ролью в тенанте.
- Плохие оценки — готовый список кандидатов в эталоны evals; экспорт — отдельная задача.
- ADR-0006 не нарушается: у `message_ratings` есть `tenant_id`. Противоречий с ADR-0023,
  ADR-0028, ADR-0036 нет: публичная история по-прежнему скрывает заменённые ответы.
