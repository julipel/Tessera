# ADR-0043: Сроки хранения данных посетителей

- Статус: принято
- Дата: 2026-10-16

## Контекст
Данные посетителей лежат бессрочно, удалить их можно только вручную (REVIEW.md: L-3, L-4,
O-9). Под 152-ФЗ и GDPR попадают:
- диалоги — тексты, ввод форм, факты и сводка в состоянии (`conversations`, `messages`);
- аргументы и результаты инструментов (`tool_calls`), оценки с комментариями
  (`message_ratings`);
- журнал хода (`agent_events`, ADR-0028) — сырые аргументы, без маскирования;
- контакты из форм (`leads`).

Заявка удаляется каскадом вместе с диалогом (L-4): как только появится удаление диалогов,
заявки пропадут вместе с ними. У `agent_events` лишний индекс `tenant_id` (префикс
составных), а под FK `conversation_id` индекса нет, поэтому удаление диалога сканирует
журнал (O-9).

Оператор ПДн — компания-тенант, платформа обрабатывает данные по её поручению. Значит, сроки
задаёт тенант, а платформа обязана их исполнять.

## Решение
1. **Сроки — секция `retention` в AgentConfig** (`packages/contracts/schemas`), в днях:
   - `conversations_days` — 180: диалог удаляется через столько дней после последнего
     сообщения (диалог без сообщений — после создания);
   - `agent_events_days` — 90: журнал хода, но не дольше `conversations_days`;
   - `leads_days` — 365: заявка — через столько дней после создания.

   У каждого поля диапазон 1–1825 дней, бессрочного хранения нет. Секция необязательна,
   без неё действуют умолчания.
   - Почему в конфиге: он версионируется, изменения логируются (T-4), правится в
     существующем редакторе админки без нового UI и миграции.
   - Откат версии откатывает и сроки. Это осознанно: конфиг — единое описание тенанта.
2. **Что удаляется.**
   - Диалог — строкой `conversations`; каскадом по FK уходят сообщения, вызовы
     инструментов, оценки и журнал.
   - Журнал старше своего срока удаляется и у живых диалогов. Разбор хода по шагам в
     админке у старых ходов пропадает, сообщения остаются.
   - Заявка удаляется целиком. Обезличивать её нет смысла: поля формы — произвольный JSON,
     а заявка без полей бесполезна.
3. **L-4:** `leads.conversation_id` — nullable, `ON DELETE SET NULL`. Заявка живёт свой срок,
   даже когда диалог уже удалён по своему.
4. **O-9:** вместо `ix_agent_events_tenant_id` — `(tenant_id, ts)` для удаления по сроку и
   `(conversation_id)` под каскад от диалога; тот же индекс под каскад —
   `message_ratings(conversation_id)`.
5. **Исполнение.** Cron воркера arq раз в сутки, в 03:17 UTC (`unique` — один запуск на
   несколько воркеров, таймаут 1 ч).
   - Идёт по всем тенантам, сроки берёт из активного конфига. Нет активного конфига или
     секции — умолчания.
   - Секция не проходит схему — тенант **пропускается** с ошибкой. Удаление необратимо, а
     умолчания могут быть короче сроков, которые задал тенант. Редактор админки такую
     секцию не сохранит; на практике это возможно только при смене схемы.
   - Сбой одного тенанта (ошибка БД, неисправный конфиг) не останавливает остальных: лог
     `retention.failed`, чистка идёт дальше. В конце задача arq завершается ошибкой, CLI —
     кодом 1.
   - Порядок: журнал, диалоги, заявки. Удаление порциями (500 строк, диалоги — по 100:
     каскад тянет их сообщения и журнал), каждая — своя транзакция. Блокировки короткие,
     прерванная чистка продолжится на следующий день.
   - Итог по тенанту — лог `retention.purged` со счётчиками и сроками.
   - Дополнение (P9-01aa): прогон по всем тенантам заодно удаляет истёкшие сессии админки
     (ADR-0036 §7). Это не данные посетителей, но задача та же — ежедневная чистка.
   - Вручную — `make retention [t=…] [dry=1]` (в проде `make deploy-retention`). `dry=1`
     считает `SELECT count(*)` с теми же условиями: ничего не блокирует, числа совпадают с
     настоящей чисткой.
   - **Гонка с ходом.** Выборка диалогов идёт с `FOR UPDATE SKIP LOCKED`: диалог, в который
     прямо сейчас вставляется сообщение (FK держит блокировку строки), пропускается до
     следующего запуска. Остаётся узкое окно: сообщение закоммичено после снимка запроса,
     но до блокировки, — тогда оно уйдёт каскадом, а ход закончится ошибкой записи
     (`turn_save_failed`). Это возможно, только если посетитель вернулся в диалог, молчавший
     весь срок, ровно в момент ночной чистки; принимаем этот риск.
   - Код: запросы удаления — в репозиториях модулей (`purge_inactive`, `purge_before`),
     политика и порции — `chat.application.retention`, обход тенантов и сессии — точка
     сборки `app/retention.py` (как `knowledge_wiring.py`), только через `public.py` модулей.
6. **Вне платформы** (`docs/deploy.md`):
   - Langfuse хранит маскированные трейсы (ADR-0032) по настройке срока хранения в своём
     проекте. Её ставит оператор, не дольше срока диалогов.
   - Бэкапы (`make deploy-backup`) содержат удалённые данные до своей ротации. Её срок
     прибавляется к сроку хранения.

## Последствия
- Данные посетителей удаляются автоматически; сроки задаёт тенант, бессрочного хранения нет.
- Первая чистка на накопленной базе удалит всё старше сроков сразу. Перед включением
  стоит посмотреть `make retention dry=1`.
- Метрики по заявкам за период дольше `leads_days` из БД не восстановить. Выгрузку
  заявок (L-5) делать с расчётом на это.
- Счётчики `retention.purged` — прямые удаления; каскадные строки (сообщения и т. п.) не
  считаются.
