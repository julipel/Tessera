# ADR-0022: Встраивание виджета — allowed_origins через CSP frame-ancestors, Origin на API — вторая линия

- Статус: принято
- Дата: 2026-10-05

## Контекст
P5-06: виджет на сайте тенанта — это `widget.js` и iframe с нашим веб-чатом
(architecture.md §14). У ключа виджета есть `allowed_origins` (ADR-0007): ключ лежит в HTML
сайта и публичен, поэтому сайты, где он работает, нужно ограничить. ADR-0007 предполагал
проверять `Origin` запросов к API.

Но чат в iframe загружается с origin нашего веб-приложения. Все его запросы к API идут с
`Origin` нашего чата, а не сайта тенанта. Проверка `Origin` на API не видит, на каком сайте
открыт виджет. Чужой сайт может вставить наш iframe с украденным ключом, и API этого не
заметит. Браузер знает предков фрейма, но API их не видит.

## Решение
1. **Основная защита — CSP `frame-ancestors` на странице iframe** (`/widget?key=…`).
   Сервер веб-чата (Next.js `proxy`) запрашивает `GET /v1/public/widget` (`X-Widget-Key`) →
   `WidgetEmbed { allowed_origins }` и ставит
   `Content-Security-Policy: frame-ancestors <allowed_origins>`. Если ключ неверный, список
   пустой или API недоступно, ставится `frame-ancestors 'none'` (закрыто по умолчанию).
   Проверку предков выполняет браузер, подделать её со страницы нельзя.
2. **Вторая линия — `Origin` на API** в общей зависимости ключа виджета
   (`require_widget_access`, ей подчиняются и public config, и API диалогов). Если `Origin`
   есть и не входит в `allowed_origins ∪ Settings.cors_origins`, API отвечает 403 `forbidden`
   (новый код в `http_error.schema.json`). `cors_origins` — свой веб-чат, с него ключ
   работает всегда. Запрос без `Origin` (серверный клиент) пропускается: вне браузера
   заголовок подделывается, от таких клиентов защищает rate limiting (P7-04).
3. **Формат origin** — как его шлёт браузер: `http(s)://host[:port]` в нижнем регистре, без
   пути, `/`, `*` и `;`. Он проверяется при загрузке YAML тенанта (`TenantSpec`) и ещё раз
   при сборке CSP. Так значение не может дописать в заголовок свою директиву.
4. CORS остаётся статическим (`cors_origins`): браузеры ходят в API только из нашего чата.
   Прямое использование API с сайтов тенантов, то есть динамический CORS по ключу, —
   вне решения.

## Альтернативы
- **Только `Origin` на API** (как в ADR-0007). При схеме с iframe не работает: `Origin`
  всегда наш.
- **Origin сайта в параметре iframe (`?origin=`) и проверка на API.** Параметр задаёт сама
  встраивающая страница, и подделать его тривиально.
- **`X-Frame-Options`.** Не умеет список origin (`ALLOW-FROM` устарел и не поддерживается),
  а `frame-ancestors` поддерживают все актуальные браузеры.
- **Виджет без iframe (скрипт рендерит чат прямо в DOM сайта).** Нужен динамический CORS
  по ключу, а стили и скрипты сайта пересекаются с чатом. Iframe изолирует и то и другое.
- **`allowed_origins` в `PublicConfig`.** Можно обойтись одним эндпоинтом, но proxy тянул бы
  весь публичный конфиг ради одного поля. Отдельный `WidgetEmbed` — узкий контракт
  для сервера чата.

## Последствия
- Страница `/widget` динамическая: на каждую загрузку iframe proxy делает запрос к API.
  Кэш `allowed_origins` в proxy — позже, при нагрузке (P7-05).
- Проверка `Origin` на API почти всегда видит наш чат. Её польза — согласованная семантика
  ключа, если браузеры когда-нибудь будут ходить в API с других origin (динамический CORS),
  и защита от неверно настроенного CORS.
- В `allowed_origins` тенанта нужно перечислить все варианты сайта (`https://shop.example`
  и `https://www.shop.example` — разные origin). Для локальной разработки и e2e — origin
  демо-страницы.
- Полноэкранный чат `/` по-прежнему можно встроить где угодно. `frame-ancestors 'none'`
  для него — отдельная мелкая задача.
